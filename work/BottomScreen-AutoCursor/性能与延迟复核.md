# BottomScreen 0.2.9 性能与延迟复核

复核日期：2026-10-31。目标设备：31.5 寸显示器，4K 160Hz / 1080p 320Hz，RX 9070。此次测试使用程序自己的窗口和 GPU 测试图，没有操作用户的游戏。

## 结论

程序没有接管点击、键盘或对局中的相对鼠标输入，输入仍由 Windows 直接交给游戏。显示反馈需要经过游戏画面捕获、GPU 复制与缩放、显示合成，因此不能保证与原生直出完全等同。本次修正了几处可避免的排队和重复工作，但没有测量实际游戏的输入到画面延迟，不能给出毫秒收益或百分比提升。

## 本版已落地的改进

| 项目 | 原来的额外工作或等待 | 0.2.8 的处理 |
|---|---|---|
| 捕获帧生命周期 | 持有捕获帧直到 Present 返回，占用捕获缓冲区 | GPU 复制指令提交后释放，再绘制和 Present；无需等待 GPU 完成，也不增加 Flush |
| 显示排队 | 沿用设备默认排队配置 | 将 DXGI 最大排队帧数设为 1，并读回验证；这不等于整条链路只有一帧延迟 |
| 待处理帧 | 可能先处理队列中的较旧帧 | 最多立即取两帧，有较新帧时释放较旧帧；不循环等待 |
| 相同源帧 | 重复复制和提交同一源时间戳的画面 | 源时间戳、尺寸、裁切都相同时复用 GPU 缓存；光标与文字也没变化则跳过提交 |
| 静止菜单光标 | 光标更新需要重画场景 | 使用已有 GPU 画面；光标样式变化时才重新复制小图，不复制整个场景 |
| 光标守护心跳 | 读取状态可能等待渲染锁 | 读取发布的不可变状态，避免 UI 心跳被 Present 阻塞 |

继续保留 WGC 最小更新间隔为零的请求、GPU 内缩放、无软件限帧，以及默认关闭性能诊断。正常模式没有逐帧日志写盘或性能日志后台任务；异常错误日志仍保留。

## 输入与光标

- 没有鼠标坐标纠正、消息转发、注入、全局输入钩子或额外的瞄准平滑。此版本不会在输入消息送入游戏之前插入等待。
- 复制出来的光标属于显示反馈；它可能比系统硬件光标更晚显示，但这不表示点击消息被延迟发送。
- 游戏有新画面时随画面更新光标。静止场景使用 8ms 定时器检查，最近捕获后约 12ms 内不抢着重画；实际调度和合成仍可能增加等待。这主要影响菜单光标观感，并非原始鼠标输入链路增加固定 8ms。
- 守护进程约 10ms 检查状态，主界面约 100ms 更新心跳；它们影响原位置光标隐藏/恢复的转换时机，不转发或缓冲游戏点击。主进程卡住/退出时依靠短期租约恢复系统光标。
- 此次新增 GPU 缓存路径验证了箭头、手形、文本、十字四种光标绘制，以及隐藏小屏光标后的画面恢复。完整系统光标隐藏/恢复集成测试在当前桌面因系统报告无可见光标而未完成；生产守护逻辑未改动，不能把 GPU 绘制通过当作全部守护行为都通过。

## 仍有的性能边界

1. WGC 与 Windows 合成器的交付节奏不由本程序完全控制。游戏 300+ FPS 不代表捕获或面板收到 300 个不同画面；320Hz 需要另行实测。
2. 4K 的源画面 GPU 复制、整屏输出清理和显示合成仍消耗带宽；缩成 24 寸不会消除这些工作。GPU 已被游戏充分占用时，捕获/合成可能与游戏争用资源。本次没有用 GPU 分析器证明具体瓶颈。
3. 使用窗口或全屏窗口化；覆盖窗口和捕获会影响 Windows 为游戏选择的呈现路径，是否增加合成等待取决于系统和驱动。独占全屏不属于保证支持的路径。
4. 本机自测读到 AMD Radeon RX 9070；没有证据表明本次由核显渲染。没有新增显卡选择 UI。若其他配置使用不同适配器，可能增加跨 GPU 传输成本，应先核查真实设备，再决定是否适配。
5. 没有加入额外睡眠、软件帧率上限、每帧 GPU 等待或 CPU 整帧读回。自测截图需要 CPU 读回，但只在显式自测中调用。
6. 暂未改成等待对象交换链、增加渲染线程或实现 HDR 浮点管线。这些涉及呈现机制和兼容性变化，缺少对照测量时不应直接认定更快。

## 帧率如何看

0.2.9 顶部数字改为统计成功提交的不同源帧。GPU 缓存画面的复制序号用于避免重复计数；只有该序号的画面首次成功 Present 后才增加一次计数，光标移动、光标隐藏、统计文字刷新以及其他缓存重绘均不增加计数。捕获端用源时间戳、内容尺寸、纹理尺寸和裁切区域区分源帧身份；不进行整帧像素比较或额外 GPU 同步。

约每秒按实际经过时间更新，静止场景可以为 0 FPS。它比包含重复提交和光标重绘的旧指标更接近游戏画面更新速率，但仍不是游戏 FPS、面板扫描输出的实测帧数或输入延迟。系统合成可能丢弃已成功提交的画面。旧版曾在 160Hz 下每秒重复提交约 320 次，其中约一半源时间戳相同；新版接近源更新率可能是预期行为。

诊断模式新增较旧队列帧替换、源画面复用、跳过重复提交及 Present 前释放捕获帧的计数。CPU 侧的 Present、复制指令耗时不代表 GPU 执行耗时，也不是输入到画面的延迟。

## 自动 HDR 修正

设置作用于所选窗口所属的游戏 EXE。默认不允许该游戏使用自动 HDR，点击“应用设置”后若配置改变，需要手动重启游戏，再刷新并选择窗口。重启 BottomScreen 不会让已经运行的游戏重新读取配置。程序只修改该 EXE 的自动 HDR 配置，保留 GPU 选择、窗口化优化和其他条目，也保留旧版 BottomScreen 的既有 Windows 首选项。

勾选“允许”表示恢复跟随 Windows 全局策略，不强制开启 HDR。单应用配置使用本机 Windows 设置实测的 `AutoHDREnable=48;`；它属于未公开稳定的注册表格式，未来系统版本可能需要适配。写入和读回失败会显示错误。输出仍为 SDR 8-bit，没有实现原生 HDR 或 HDR 到 SDR 的色调映射。

## 已验证与待实测

- 当前发布候选可执行文件的自身窗口/GPU 自检通过 186 项：4K/1080p 尺寸计算、24/27 寸、无边框源、裁切与尺寸变化、GPU 像素、缓存重绘、四种光标、HDR 假路径集成、重启标记、控件布局、日志、排队上限与捕获帧释放顺序。新增检查覆盖缓存多次重画只计一次、四种光标及光标隐藏不计帧、仅复制未显示不计帧、下一张新画面计一次和静止源帧率归零。
- 自测记录使用 RX 9070，排队上限读回为 1。本次测试源未复现旧实战中的重复时间戳比例，因此没有据此计算游戏性能提升。
- 尚未完成：真实 CS2 的修改前后同场景对照、1080p 320Hz 稳定吞吐、游戏自动 HDR 的视觉生效检查，以及高速摄影/专用设备的输入到画面延迟测量。

用户实际验证时可保持同一游戏设置、帧率限制和显示模式，分别比较原生与开启 BottomScreen 的操作感和帧时间。仅看平均 FPS 不能判断输入反馈延迟；正常使用保持诊断关闭即可。
